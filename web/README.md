# Clinic websites from one repo (Astro monorepo demo)

Two **fictional** Austin, TX dental clinics built from one shared theme. Each site is only data:
`clinic.yaml` (name, NAP, hours, dentists, services, prices, insurance, FAQ), `theme.json` (design tokens)
and Markdown posts. Everything else is generated. Nothing here is deployed; all checks run locally.

## Architecture

```
packages/schema   Zod schemas: clinic.yaml, theme.json, post frontmatter. Bad data = failed build.
packages/theme    Astro integration + layouts + components. Injects every route:
                  pages, sitemap.xml, robots.txt, llms.txt, favicon, og.png, JSON-LD.
sites/clinic-a    Bluebonnet Hollow Dental  (serif, blue, split hero)   copied from the QA fixture
sites/clinic-b    Copper Wren Dental Studio (sans, copper, centered hero, different hours/services/slugs)
tools/            build, validators, golden snapshots, scale proof, add-client, tests
golden/           approved HTML of every page (what "unchanged" is compared against)
reports/          JSON written by the tools; the results below are generated from it
```

A site folder holds `clinic.yaml`, `theme.json`, `src/content/posts/*.md` plus 4 boilerplate files (about 20 lines in total).
There is no page code per site. The facts a post is checked against (phone, hours, prices, carriers) are in
`clinic.yaml`, the same file the website renders. For clinic-a that file is a **copy** of the QA gate's fixture
(`demo/qa/fixtures/clinic.yaml`, owned by the QA terminal), extended with website fields; `tools/check-fixture-parity.mjs`
checks one way only: every fixture key and value must still be present in the copy. If the QA fixture changes, run it.
The check fails (it does not skip) when the fixture is missing.

SEO is generated from the data, not written by hand: JSON-LD (`Dentist`, `FAQPage`, `BlogPosting`, `BreadcrumbList`),
sitemap with `lastmod` (post `updated` date, else the clinic's `updated` date), robots.txt (search/answer bots allowed,
training bots per client in `seo.allow_ai_training`), canonical, Open Graph, `llms.txt`, generated internal links.
No `aggregateRating`, `review` or award is generated: the schema allows no testimonials or awards, and the validator
rejects those properties in any JSON-LD block. JSON-LD and theme values are escaped/allow-listed so client-supplied text
cannot close a `<script>` or `<style>` block.

## Commands (from `demo/web`)

```bash
npm install
npm run build                       # build all sites -> sites/*/dist, timings in reports/build.json
npm run check                       # all gates (needs a local Chrome or Edge for the browser checks)
npm test                            # tests of the tooling itself (gates fail when they should)
npm run golden:snapshot             # save current dist as the approved golden copy
npm run golden:diff                 # compare dist with golden (changes only inside <footer> are allowed)
npm run prove:scale                 # template change -> diff across all sites (rebuilds, restores files)
node tools/selftest.mjs             # inject known defects into built pages, confirm each gate catches them
node tools/render-results.mjs       # rewrite the results block below from reports/*.json
node tools/add-client.mjs clinic.yaml [--theme theme.json] [--posts dir] [--build] [--force]
node tools/remove-client.mjs <id>
```

All tools exit non-zero on failure. A gate that examines nothing (unknown `--site`, empty `golden/`, no HTML in `dist/`,
missing QA fixture) fails instead of passing.

## How the scale proof works

`npm run prove:scale` first checks that the current build equals the approved `golden/` (which it never rewrites),
then edits one template (`Footer.astro`), rebuilds all sites and compares every page with a scratch snapshot.
"Only the footer changed" means: HTML outside `<footer>` is byte-identical and the visible text outside it is identical. The one exception is Astro's scoped-style ids (`data-astro-cid-<hash>`): Astro hashes the absolute path of the shared theme's components, so the hash depends on the checkout folder and the OS. The diff renames each id in order of first appearance before comparing (`stableCids` in `tools/golden.mjs`, with a test), so the golden snapshots pass on any machine and in CI.
A negative control (editing the CTA outside the footer) must be flagged, and the templates are restored and rebuilt at the end.
Measured on 2 sites; it shows the mechanism, not behavior at 50 sites.

## Add a client

`node tools/add-client.mjs new-clinic.yaml --posts ./posts --build` validates the YAML and the posts first
(readable errors; a real-looking phone number or a non-`.example` domain is rejected; nothing is written on error),
scaffolds `sites/<id>/`, derives a contrast-safe palette if no `theme.json` is given, builds, and runs the JSON-LD,
link/SEO and weight checks. Timing of the last run is in the results block.

## Limits

- Demo clinics are fictional (`.example` domains, 555-01xx phones, disclosure in every footer). Not deployed anywhere.
- 3 posts per clinic, adapted from the QA fixtures; clinic-b's posts are rewritten text, not search-and-replace copies.
- Posts keep factual sentences (phone, hours, prices) in prose, as the QA gate expects. Only the site-level pages derive them from data.
- `lastmod` for non-post pages is one date per clinic (`updated`), not per page.
- No photos, only a generated social card; a real client site needs an image pipeline.
- Hosting, analytics and indexing APIs are out of scope (no accounts were created).
- The tools were run on Windows only; they avoid shell and Windows-specific paths, and have a test for paths with spaces, but there is no Linux/macOS CI run yet.
